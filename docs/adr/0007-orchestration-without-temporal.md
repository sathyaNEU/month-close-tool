# ADR-0007: orchestration without Temporal (leases, fencing, outbox, scheduler claims)

Status: accepted with Stage 1a. Date: 2026-09-27. Spike S5'. Amends ADR-0006 (the scheduler uses claim rows, not advisory locks).

## Context

ADR-0006 dropped Temporal, so the two guarantees it gave us for free have to be built and proven in our own code: one writer per resource at a time, and side effects that happen once even when processes crash or messages are delivered twice. The control plane is a Databricks App with one to five instances, the state lives in Lakebase Postgres, and the work runs as Lakeflow jobs that we reach only through the Jobs API. Three facts shaped the design. The Jobs API documents the `idempotency_token` on `run-now` but not how long Databricks remembers it. A session-level Postgres advisory lock held through a connection pool is lost silently when the pool recycles the connection (and is kept by a connection that goes back to the pool), so it cannot guard work across instances. A job that is running cannot be recalled, so whatever a stale writer might do has to be caught by the writer itself.

## Decision

The writer lease is a row in `leases` with a `fencing_token` that increases on every grant and re-grant, and the holder is a run attempt. The lease has no timer. It is released only in the same transaction that records the attempt as terminal (`status.state == TERMINATED`), and after an `INTERNAL_ERROR` or `CLOUD_FAILURE` termination it stays held through a quarantine (10 minutes by default) in case the cluster is still writing. When the Jobs API cannot be reached the status is `UNKNOWN`, nothing transitions, the lease stays held, and new starts get a 409. The only way out is the audited break-glass `force_release`, which also bumps the token. Every timestamp that is compared comes from Postgres `now()`, and every audit row goes to `lease_events`, which the app role can insert and read but never change.

Fencing detects what the lease prevents. A job's first action is to append its token to `ops.writer_claims`, and it checks for a higher token before its commit and again after it, exiting with code 3 and a `fenced` result if it finds one. Every Delta commit carries `userMetadata` with `run_id`, `attempt` and `fencing_token` (the eighteenth parity feature, ADR-0002). The residual window is real and documented: a zombie that has passed its last check can still commit before a newer claim appears, which a strict xfail pins in `engine/tests/spark/test_fence.py`. What keeps that window from mattering is prevention: a new grant happens only after the previous attempt is terminal and jobs have `max_retries: 0`, so the platform itself never starts a second writer. The one realistic outside source of a zombie is a person pressing "Repair run" with stale parameters, and Stage 10 removes it with job permissions in the bundle (only the app's service principal can run the engine jobs, people get view access). Until Stage 10 there is no workspace to set permissions on, so locally the protection is the lease, `max_retries: 0` and fencing.

Side effects leave through a transactional outbox. The request that starts a run stores its `Idempotency-Key`, takes the lease, inserts the run and attempt, and publishes `run.submit` in one transaction, and request handlers never call external systems. Only the relay submits. It calls `run-now` with the attempt's token (`close-{env}-{job_key}-{run_id_hex}-a{NN}`, 64 characters at most), and because we do not know how long the token is remembered, it does not rely on it alone. On any redelivery (`OutboxEvent.delivery > 1`) it first searches `runs/list` for a run carrying this `run_id` and `attempt`, and once the run is older than the token window (1 hour) it only searches, ending the attempt as `submit_failed` when nothing is found. A duplicate therefore needs both a missed lookup and a forgotten token, and even then `max_concurrent_runs: 1` with queueing makes the duplicate run after the first one, over a partition the first one already wrote. The `run.submit` and `run.cancel` topics are never dead-lettered: their handlers end their own loops (submit through the search above, cancel by becoming a no-op once the attempt is terminal), and giving up earlier would leave the lease held by an attempt that nothing observes any more.

Periodic work (the outbox relay and the run poller) is claimed per task through a compare-and-set on `scheduler_tasks.next_due_at`, in Postgres time, instead of an advisory lock. Each due tick is claimed by exactly one instance, a crash after claiming loses that tick but never duplicates it (every task is idempotent), and the next tick goes to whichever instance is alive. The claim transaction sets `idle_in_transaction_session_timeout = 500ms` and `lock_timeout = 1s`, because an instance frozen between its `UPDATE` and `COMMIT` would otherwise hold the row lock for the server-wide idle timeout (30 s). The claim rows are registered again every minute, so a row that disappears comes back instead of silently stopping its task.

## Consequences

Gate 1a proves each piece under fault injection rather than by argument. The platform suite covers 20-way lease races, the append-only audit trail, 100 outbox events through three crash points, a long outage that must not dead-letter a submit, a response lost after `run-now` followed by a forgotten token, and two scheduler instances over 100 intervals, including one frozen mid-claim. The end-to-end suite repeats the important cases against the real stack: the app killed after accepting a run, killed during `run-now` with a 5 s token memory, killed while the job runs, the jobs service restarted mid-run (quarantine), the job finishing while the app is down, a Jobs API outage, a zombie in its own container, and two app instances killed and frozen in turn. A final check walks the whole lease history and asserts that every grant came after the previous attempt was terminal and that no external run was ever duplicated.

One operational rule follows from putting the tokens in Postgres and the claims in the lake: fencing tokens must never go backwards. If the control-plane database is restored from an older backup, every job fences itself (safe, nothing is written, the run fails with a `fenced` error) until an operator raises each lease's `fencing_token` above the highest claim in `ops.writer_claims` for that resource. The end-to-end suite demonstrates both halves (`test_95_token_rollback`). Today that recovery is a manual `UPDATE` run by the platform owner. Stage 10 adds it to the runbook as an audited break-glass command, with its own `lease_events` type, next to `force_release`.

We would revisit this if Databricks documents a token retention we can rely on (the search on redelivery could then be skipped), or if job volume ever makes the per-resource lease a bottleneck, which at 7 users and a handful of match sets it is not.
