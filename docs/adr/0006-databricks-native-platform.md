# ADR-0006: run the platform on Databricks (App, Lakebase, Lakeflow Jobs) instead of Kubernetes and Temporal

Status: accepted. Date: 2026-09-27. Amends D5, D6, D7, D12, D13, D14, D15 and Stages 1, 10 and 11 in the roadmap. Amended by ADR-0007: periodic work runs under per-task claim rows, not an advisory lock.

## Context

After Stage 0 the user confirmed the platform will have 7 users, all on the accounting team, and still has to be enterprise grade. At this size, enterprise grade means solid controls, security, audit, disaster recovery and change management rather than scale. The heavy compute already runs as Databricks jobs, so the application tier (API, workflow logic and later the UI) is small. Running EKS, Argo CD and a self-hosted Temporal cluster for that tier would cost more effort than the application itself, and none of it is something an auditor asks for.

We checked the current Databricks documentation (pages dated September 2026) before deciding. Databricks Apps accepts a custom start command in `app.yaml`, so a FastAPI app runs under uvicorn on `$DATABRICKS_APP_PORT`. Users sign in with workspace SSO, access is granted with `CAN USE` to users or groups, and each app has its own service principal, with optional on-behalf-of-user authorization. An app can run on 1 to 5 instances with rolling, zero-downtime deployments ("a single instance failure or restart doesn't take the app offline"), in sizes from Medium (2 vCPU, 6 GB) to XLarge (12 vCPU, 48 GB). It can have Lakebase, Lakeflow jobs, SQL warehouses and secrets attached as resources, and it can be deployed with Declarative Automation Bundles. The docs give no SLA or multi-AZ statement for Apps, while Lakebase (GA on AWS since January 2026) does have HA and an SLA.

## Decision

The user chose the Databricks-native option and to drop Temporal, so production looks like this. The backend (FastAPI, and later the UI it serves) runs as one Databricks App with two or more instances. Configuration, workflow state, audit, outbox and leases live in Lakebase Postgres, which is attached to the app as a resource. The matching and journaling engine runs as Lakeflow jobs (the wheel and thin notebooks from Stage 0), and the app, jobs and database are deployed together with bundles from GitHub Actions. There is no Kubernetes, no Argo CD, no container registry and no Temporal in production.

Temporal gave us two guarantees for free, and they now need explicit replacements. The first is one writer per match set. It becomes a lease row in Postgres with a fencing token that increases on every grant. The token is passed to the job and checked when the job commits, the Jobs API `idempotency_token` stops duplicate submissions on retry, and the app waits for the previous run to reach a terminal state before it hands the lease on. The second is applying manual commands one at a time. It uses the same lease, so command batches and scheduled runs for a match set never overlap. Schedules move to Lakeflow job schedules. Approval reminders, escalations and the outbox relay run in the app under a Postgres advisory lock, so only one instance does that work even when several are running (amended by ADR-0007: a per-task claim row replaces the advisory lock, because a pooled connection can lose a session lock silently).

Identity comes from the Databricks Apps proxy through the forwarded headers, and the app trusts those headers only because the app is reachable only through that proxy. Roles, entity scoping and segregation of duties stay inside the app (Stage 4), because the workspace permission only decides who can open the app, not what they are allowed to approve. Locally, a development-only shim sets the same headers, so role and SoD tests use real code paths.

For local development, Kubernetes is replaced by Docker Compose. It runs Postgres 17 as the Lakebase stand-in, SeaweedFS as the S3 stand-in, a Spark Connect server for the read path, and a local job runner that mimics the Jobs API calls we use (submit with an idempotency token, status, cancel, logs). The `ComputeBackend` and `QueryEngine` interfaces from the plan stay the same, and only their local implementations change.

## Consequences

Everything built in Stage 0 stays valid, including the contracts, the engine, the Delta parity suite, the lint, the wheel, the notebooks and the gate. Local development needs much less memory, roughly 8 to 10 GB for Docker instead of the 12 GB we asked for with kind, and Stage 1 will measure the real number. Stage 1 is re-specified around Compose, the local job runner, the lease and fencing design and the header-based identity, and it goes to the user for approval before we build it.

There are new prerequisites before production. The 7 accountants must be workspace users signing in through SSO, with `CAN USE` on the app through a group, and the security team has to approve Apps and Lakebase. Network policies for app egress are only available on the Enterprise tier. Because the docs state no SLA for Apps, Stage 11 has to decide whether two instances plus rolling deploys meet the close-week availability target, or whether we need a documented fallback. The read path in production pairs naturally with a SQL warehouse, which is still decided in Stage 10 behind a differential test (ADR-0005).
