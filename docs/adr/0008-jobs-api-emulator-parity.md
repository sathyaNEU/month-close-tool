# ADR-0008: a local Jobs API 2.2 emulator driven by the real databricks-sdk

Status: accepted with Stage 1a. Date: 2026-09-27. Spike S6'.

## Context

Production runs the engine as Lakeflow jobs that the app reaches through the Jobs API with the official `databricks-sdk`, and local development must run with no cloud (ADR-0006). If the local stack used a different client path, the code that decides when a lease may move on (status mapping, idempotent submission, cancellation, output retrieval) would only ever run in production. The installed SDK (`databricks-sdk==0.143.0`) calls these endpoints for our use: `POST /api/2.2/jobs/run-now`, `GET /api/2.2/jobs/runs/get`, `POST /api/2.2/jobs/runs/cancel`, `GET /api/2.2/jobs/runs/get-output`, `GET /api/2.2/jobs/runs/list` and `GET /api/2.2/jobs/get`, plus `/.well-known/databricks-config` at start-up and the OIDC endpoints for machine-to-machine OAuth, which is how a Databricks App authenticates.

## Decision

We built the smallest emulator the SDK needs (`services/jobs_emulator`) and point the unchanged SDK and `DatabricksJobsBackend` at it. It serves the endpoints above with the 2.2 `status` object (`state` plus `termination_details` with `type` and `code`), the legacy `state` block as a fallback, `tasks[].run_id`, and output keyed by the task run id (a job run id gets the same 400 Databricks returns). Errors use the Databricks shape, `{"error_code", "message"}` with a matching HTTP status. Tokens come from `/oidc/v1/token` with client credentials, like the app's service principal in production, and a PAT is accepted for tests.

Access tokens are self-contained signed values (like the workspace's JWTs), so they stay valid across an emulator restart. The first version kept issued tokens in memory, and the end-to-end suite caught what that does: after the jobs service restarted, the app kept its cached token, the SDK refreshes a token only when it expires, so every call failed with a 401 and the run stayed `UNKNOWN` (lease held, safely) for up to an hour. So besides fixing the emulator, `DatabricksJobsBackend` now drops its client when a call is rejected as unauthenticated, and the next call builds a new client with a fresh token, which also covers a revoked token or a rotated secret in production.

Job definitions come from the same `engine/databricks.yml` bundle we deploy. The parser accepts a strict subset (parameters, exactly one `python_wheel_task`, `timeout_seconds`, `max_concurrent_runs`, `queue`, `max_retries` which must be 0), rejects unknown keys, and rejects target overrides of parameters, tasks, timeout, concurrency or queueing, so the local job cannot drift from the deployed one. Each run is its own process group started with the same `spark-submit` command a cluster would run, with the jars pinned in `tools/jars.lock` and the S3 writer key passed as environment, never on the command line. Cancel sends SIGTERM and then SIGKILL after 20 s, `timeout_seconds` is enforced the same way, state is kept in SQLite on a volume, and a restart marks any run that was active as `INTERNAL_ERROR`, which is what a lost cluster looks like. A job never sees the emulator's own credentials or the raw S3 keys.

Test-only switches exist when `EMULATOR_ALLOW_FAULTS=1` (local only): a Jobs API outage (503 on every Jobs call), a `run-now` that creates the run and then holds its response, a short idempotency-token memory, revoking every access token issued so far, a per-job timeout, and a listing of every run for assertions.

## Consequences

Every local run exercises the production client path, and the gate proves the parts that matter with the SDK itself: idempotent `run-now`, output from the task run, failure and cancel mapping, timeouts, the search that replaces a forgotten token, outages mapping to `UNKNOWN` and never to a terminal state, and M2M OAuth. The emulator does not model multi-task jobs, clusters, repair runs, job permissions or real queueing between jobs (it runs one job at a time, like our single-node budget), so none of those may be relied on until Stage 10 runs the same suite against a real workspace. Stage 10 also confirms what the documentation leaves open: how long `idempotency_token` is remembered, whether the Apps proxy overwrites client-supplied `X-Forwarded-*` headers, and the exact termination codes a real cluster loss produces.
