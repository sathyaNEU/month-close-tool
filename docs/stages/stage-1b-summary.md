## What Stage 1b delivers

The app can now read the lake, and every read goes through one typed path ([ADR-0009](../adr/0009-read-path-query-specs-final.md)). A request is a `QuerySpec` that names a registered table and gives the columns, filters, order and page size, and the engine adds the caller's entity filter itself, so no request can reach another entity's rows. Every page of a paging session reads the Delta version pinned on the first page, and the cursor that leads to the next page is signed and bound to that user, that query and that version, so it cannot be forged, borrowed or replayed against another query. The app reaches Spark only through a new `spark-connect` service that holds the reader-only S3 key, so the app itself still has no S3 keys, and a write through Spark Connect fails with 403.

The same query semantics have three executors, and the gate proves they agree. The DataFrame backend over Spark Connect is what the app uses today, the SQL renderer produces parameterised SQL for a Databricks SQL warehouse (every caller value bound as a named marker) in case Stage 10 moves the read path to a warehouse, and the reference evaluator in plain Python is the oracle for both.

The smoke job now also writes a run manifest to the lake, one row per entity with its row count and digest, tagged with the attempt and the fencing token. The smoke GET for a succeeded run reads its result from that manifest through a QuerySpec, and only the rows written by that attempt with its own fencing token count, so nothing from a zombie writer in the residual window ([ADR-0007](../adr/0007-orchestration-without-temporal.md)) can surface (two different digests for one entity are answered with a 500 "Result integrity error"). Two new endpoints, `/rows` and `/totals`, page and group a run's rows.

Around the read path, the stage adds the catalog spike, CI and image scanning. The Unity Catalog spike ran the engine's catalog code paths against Unity Catalog OSS 0.6.0, and all of them work once the catalog has a managed storage location ([ADR-0010](../adr/0010-unity-catalog-spike.md)). Two GitHub Actions workflows mirror `make ci` and the Compose end-to-end flow, with every action pinned to a commit SHA and both files clean under actionlint and zizmor, and trivy scans our two images and our Dockerfiles and writes a CycloneDX SBOM for each image. The criteria table below carries the measured evidence for each gate item, followed by the Stage 1a criteria run again as regression.

## Found and fixed while building and testing

1. Spark Connect keeps query tags per thread, and the web server reuses its threads, so without cleanup every query would carry the tags of all earlier queries on its thread, and a timeout interrupt aimed at one of those could stop it. Each query's tag is now removed in a `finally` block.
2. The first trivy scan flagged known vulnerabilities in jars that `close-spark` carried but Spark never loads. The Stage 1a jar lock also pinned artifacts that pyspark already ships in its own distribution, and since Spark loads its own copy first, those were dead code that brought their vulnerabilities into the image. `tools/lock_jars.py` now leaves out every artifact pyspark ships, in any version, so the lock holds 15 jars instead of 28.

## Where the build differs from the approved spec

1. `spark-connect` has a 2048m memory limit instead of 1792m. During development the 1M-row benchmark took the JVM close to 1792m (the 1 GiB heap plus off-heap memory), which left too little headroom (the kernel kills a container whose processes outgrow its limit), so I raised the limit rather than shrink the heap.
2. The memory budget is 8.5 GiB instead of 6.5 GiB, which follows from your choice to give Docker more memory for this stage (the Docker VM now has 11.67 GiB, and the gate checks for at least 9.5 GiB).
3. The smoke GET reads from the lake only once a run has succeeded, because before that there is no manifest to read. A running or failed run still shows the job's reported status, filtered to the caller's entities, as in Stage 1a.
4. The catalog spike runs as its own Compose project (`compose.uc.yaml`, started by `make uc-spike`) instead of a `+uc` profile of the main stack. That way it never counts against the main stack's memory, and it publishes the catalog server on 127.0.0.1 only while the spike runs.
5. trivy gates `close-spark` only for what we add to it, not for the Apache Spark distribution inside it. This is the first decision below.

## Needs your decision

1. The trivy policy. `close-app`, the image we deploy, is gated in full. `close-spark` is the local stand-in for the Databricks runtime and is never deployed, so it is gated for everything we add to it (our pinned jars, our wheels and the Python packages we install), while findings inside the Spark distribution's own jars are reported but not gated, because they change only with the pinned Spark version (which mirrors DBR 18) and production runs Databricks' own patched runtime. My suggestion is to accept it.
2. Two new trivy waivers, both expiring on 2026-12-31 and owned by the platform engineering lead, like the Stage 0 one. The first is CVE-2026-25087, which is the CVE name of the pyarrow advisory already waived as PYSEC-2026-113. The second covers the AWS SDK bundle jar that hadoop-aws 3.4.2 requires, which cannot move on its own because hadoop-aws must match the Hadoop that pyspark bundles, and which only ever talks to SeaweedFS on the private Compose network. My suggestion is to accept both.
3. D19 (whether the ERP or Databricks is the GL book of record) is still open, and it is needed at the Stage 5 gate.
